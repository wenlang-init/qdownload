## 2. 技术选型

| 项 | 选择 | 说明 |
|---|---|---|
| Qt | **Qt 6.12**（本机已装 6.12.0，另有 6.9.3 可回退） | Qt 6.8+ 的 QML 工具链与 Android 支持最稳 |
| UI | **Qt Quick + Qt Quick Controls 2 + Qt Quick Layouts** | 声明式、移动端手感好、一套界面三端自适应 |
| 语言 | C++17（内核）+ QML（界面） | 逻辑与表现彻底分离 |
| 构建 | CMake + `qt_add_qml_module` | QML 模块化注册，Android 打包用 `QT_ANDROID_PACKAGE_SOURCE_DIR` |
| 网络 | `QTcpServer/QTcpSocket` 异步 + `QUdpSocket` 组播 | 事件驱动，单线程即可支撑 |
| 序列化 | 控制通道 `QJsonDocument`；数据通道裸二进制 | 可读 vs 零开销 |
| 持久化 | SQLite（`QSqlDatabase`）：断点表、信任设备表；`QSettings`：配置 | 断点与信任关系必须落盘 |
| 并发 | 网络在 UI 线程（异步）；写盘/哈希走 `QThreadPool` | 不阻塞渲染 |
| 加密 | `QCryptographicHash`（SHA-256）+ `QMessageAuthenticationCode`（HMAC-SHA256） | Qt 自带，无需第三方库 |

### 为什么 UI 用 QML 后，文件列表改"平铺"而不是"树"

QML 的 `TreeView` 在 Qt 6 里属于 `QtQuick.Tree` 附加模块，delegate 嵌套深、移动端性能差。**统一改成"当前目录平铺列表 + 面包屑导航"**：

- 桌面端：列表上方一行面包屑 `根 / docs / 2026`
- 移动端：面包屑收成一行可横滑，返回键回上级
- 三端同一套 delegate，代码量减半，触摸体验一致

代价是不能像资源管理器那样展开树。文件浏览场景里"进目录"的操作成本很低，可接受。

## 4. 组网与发现

- 组播组 `239.255.42.99:45454`，TTL=1，每 **3 秒** `ANNOUNCE`，**10 秒**超时判离线
- 报文：`{peerId, name, platform, ctrlPort, sharing, write, version, ts}` —— 只带能力状态，**不含目录内容、不泄露任何文件名**
- `write` 字段让未连接的设备也能在下拉框里直接看到"对方是否收文件"，避免点进去才被拒
- `peerId`：首次启动生成 UUID 存 `QSettings`，长期不变（断点归属、信任关系都靠它）。
  **同机多开时按实例编号分开存**：第 2 个进程起各自用 `data/instance-<n>/settings.ini`，
  否则两个进程同一个 peerId，收端按 peerId 去重会把对方的心跳当成自己的回环包丢掉
- 兜底：组播被拦时支持手动添加 `IP:端口`
- **Android 必须持 `WifiManager.MulticastLock`**，否则收不到组播（最常见坑）

端口：`45454/udp` 发现；`45455/tcp` 控制（被占用则 +1 并在心跳里广播实际端口）；数据通道由服务端从 `45456+` 端口池分配。

### 4.1 实现备注（M2 落地时确认）

- socket 用 `ShareAddress | ReuseAddressHint` 绑定：同机多实例可同时收组播，联调必需。
- **实例编号（同机多开）**：`InstanceGuard` 在启动时用 `data/instance-<n>.lock`（`QLockFile`）
  抢占编号，1 = 主实例，2..8 = 副实例。副实例有自己的 `settings.ini`（peerId 因此天然不同）、
  默认名带 ` (n)` 后缀；控制/数据端口由原有的 +1 顺延逻辑各找各的，实际端口随心跳广播。
  锁在正常退出时释放，硬杀后按 PID 判死回收（5 秒宽限），所以"关掉再打开"仍然是主实例。
  `--instance <tag>` 仍可强制指定 peerId。
- **peerId 的本机唯一性（M14）**：实例编号只能解决"同一个 data 目录"，两个**不同目录**的
  副本（整份拷过去、或搬来一个 `data/`）会各自带着同一个 peerId 跑。所以启动时还要在
  **机器级目录**（`GenericCacheLocation/qdownload/instances/peer-<id>.lock`）认领一次：
  被活进程占着就换一个新 UUID 落盘，并给默认名加编号。命令行强制的 `--instance` 不改写，只告警。
  任一侧拿不到唯一 id，两端都会把对方心跳当"自己"丢掉，表现是互相发现不了。
- **关闭共享继续广播**（`sharing=false`），否则对端下拉框里那台机器会消失，用户会误判为网络故障。
- 判在线只用本机接收时间，不信报文 `ts`（跨设备时钟不同步，会算出永远在线）。
- 提速：启动后 300ms / 900ms 各补发一次；收到陌生主机立即回一发（限流 1 秒），首次互见从最坏 3 秒降到 1 秒内。
- `write` 字段随心跳一起发，未建立的设备也能在下拉框看到「可上传 / 只读 / 未共享」。
- **多网卡逐条发送（M8 已实现）**：老实现只调一次 `writeDatagram` 交给系统路由，装了 VMware / Hyper-V / VPN 的机器上默认出接口经常不是连内网那张，心跳就悄悄发丢了。现在给每张可用网卡开一个专用 `QUdpSocket` 并 bind 到它的 IPv4 地址——绑定哪个地址，出接口就是哪张网卡。
  - **没走 `QNetworkDatagram::setInterfaceIndex`**：Qt 6.12 在 Windows 上调用返回成功（`writeDatagram` 返回整包长度），但包实际一份都没出去，用独立监听端验证过。所以换成 bind 方案。
  - 每 15 秒重新枚举网卡：换 WiFi / 插网线 / VPN 连断时自动 join 新网卡，消失的 group 关系 leave 掉。
  - 同一轮心跳会经多张网卡各到一份，收端按 `peerId` 合并：800ms 内状态没变化就只刷新 `lastSeen`，不重复发信号；地址优先保留非回环的那个，避免同机双实例时地址在 `127.0.0.1` 与 `192.168.x.x` 之间跳。
  - 实测（本机 8 个 IPv4 接口）：5 张可用网卡全部发送成功，对端发现的地址是 WLAN 的 `192.168.31.210` 而不是虚拟网卡。

## 5. 通信协议

### 5.1 控制帧（定长头 + JSON）

```
 0        3 4     5 6            9
 +---------+-------+--------------+-------------------+
 | "QDL1"  | type  |  len (u32be) |  payload (JSON)   |
 +---------+-------+--------------+-------------------+
```

`MessageCodec` 累积缓冲到 `9+len` 才切帧；`len` 上限 8MB，超限直接断开。

### 5.2 消息表

| type | 方向 | 用途 | 鉴权要求 |
|---|---|---|---|
| `HELLO` / `HELLO_ACK` | C→S / S→C | 握手，ACK 携带 `nonce` | 无 |
| `AUTH_REQ` / `AUTH_RESP` | C→S / S→C | 令牌挑战应答，返回 `perm` | 无（凭 token） |
| `PAIR_REQ` / `PAIR_CHALLENGE` | C→S / S→C | 发起配对，返回 nonce 与提示 | 无 |
| `PAIR_RESP` / `PAIR_OK` / `PAIR_FAIL` | 双向 | 提交配对码摘要，下发令牌 | 无（凭配对码） |
| `LIST_REQ` / `LIST_RESP` | C→S | 列目录（分页） | **需已配对** |
| `STAT_REQ` / `STAT_RESP` | C→S | 单文件元数据 / fileKey | 需已配对 |
| `DOWNLOAD_REQ` / `DOWNLOAD_ACCEPT` | C→S / S→C | 申请下载（续传带 `fileKey`+`segmentDone`），返回**每段**的数据端口+一次性令牌 | 需已配对 |
| `CHECKSUM_REQ` / `CHECKSUM_RESP` | C→S / S→C | 取整文件 SHA-256（M13 起降级为**兜底**通道：正常路径是随表下发 / 推送） | 需已配对 |
| `CHECKSUM_PUSH` | 双向 | 本次传输的整文件摘要算好了，随控制通道推给对端（M13，数值 26） | 需已配对 |
| `DELETE_REQ` / `DELETE_RESP` | C→S / S→C | 删共享根里的一个文件；需写权限，只删普通文件（M14，27/28） | 需已配对 |
| `UPLOAD_REQ` / `UPLOAD_ACCEPT` | C→S / S→C | 申请上传（带 `segments`），ACCEPT 返回各段令牌与**服务端权威 offset / 分片进度** | **需 perm=rw** |
| `UPLOAD_DONE` | S→C | 上传落盘结果（`ok` / 实收字节 / 最终文件名 / 全量 SHA-256 / 失败原因） | 需已配对 |
| `PERM_UPDATE` | S→C | 广播写权限开关 / 策略 / 单设备权限的变更，即时生效 | 需已配对 |
| `CANCEL` | 双向 | 取消传输 | 需已配对 |
| `PING` / `PONG` | 双向 | 保活（15s 空闲） | — |
| `ERROR` | 双向 | `{code, message, reqId}` | — |

错误码约定：`401` 未配对 · `403` 权限不足 · `404` 路径不存在 · `409` fileKey 冲突 · `429` 配对尝试过多 · `507` 磁盘满。

### 5.3 报文示例

```json
// HELLO_ACK
{"type":"HELLO_ACK","peerId":"b7f1...","name":"客厅PC","platform":"win",
 "nonce":"9f3ac1e28b4d5077","protoVer":1,"needPair":true}

// AUTH_REQ（token 不裸传，只传 HMAC）
{"type":"AUTH_REQ","tokenId":"tk-42","mac":"c1a9..."}

// AUTH_RESP
{"type":"AUTH_RESP","ok":true,"perm":"rw","displayName":"我的笔记本"}

// LIST_REQ / LIST_RESP（M4 已实现）
{"type":"LIST_REQ","reqId":"r-17","path":"/docs","offset":0,"limit":200}
{"type":"LIST_RESP","reqId":"r-17","path":"/docs","offset":0,"total":37,
 "entries":[{"name":"报告.pdf","isDir":false,"size":1234567,"mtime":1698000000}]}
```

`entries` 里**不带 `fileKey`**：按 §6.1 的算法，每个条目要读首尾各 1MB，
200 个条目就是 400MB 随机读，列表会卡住十几秒。fileKey 改由 `STAT_REQ`
（或首次 `DOWNLOAD_REQ`）按需计算一次并缓存——列表只依赖 `stat` 就能拿到的
`size` + `mtime`，这两项加上 `name` 已足够客户端判断"是不是同一个文件"。

分页语义：`total` 是过滤后的总数，`offset` 是本次起始下标，`entries.size()`
是本次条数。客户端滚到底用 `offset = 已有行数` 再要一页；`offset != 当前行数`
的响应一律丢弃（中间丢页比留空洞安全）。

错误码按原因区分，客户端据此显示不同文案：`401` 未配对 · `403` 对方已关闭共享
· `404` 路径不存在 · `400` 路径非法/越界 · `500` 读取失败。

```json
// DOWNLOAD_REQ / DOWNLOAD_ACCEPT（M5 已实现）
{"type":"DOWNLOAD_REQ","reqId":"d-1","path":"/big.bin","offset":0}
{"type":"DOWNLOAD_ACCEPT","reqId":"d-1","transferId":"t-3f9a12","token":"<64 hex>",
 "port":45456,"name":"big.bin","size":1258291200,"offset":0,"fileKey":"k-9f2e..."}

// UPLOAD_REQ（被拒时返回 403；M7 已实现）
{"type":"UPLOAD_REQ","transferId":"u-3","dir":"/inbox","name":"a.zip",
 "size":88123456,"offset":0,"fileKey":"k-9f2e"}

// UPLOAD_ACCEPT（name 是主机定下的落地名，可能被改成 "a (1).zip"；offset 以主机为准）
{"type":"UPLOAD_ACCEPT","reqId":"u-3","transferId":"u-3","token":"<64 hex>",
 "port":45456,"name":"a.zip","path":"/inbox/a.zip","size":88123456,"offset":41943040}

// UPLOAD_DONE（主机落盘 + 全量摘要完成后回一条，客户端据此收尾）
{"type":"UPLOAD_DONE","transferId":"u-3","ok":true,"size":88123456,
 "name":"a.zip","path":"/inbox/a.zip","sha256":"6ca57e82..."}

// PERM_UPDATE（主机拨动写权限开关 / 改策略 / 改单设备权限，都推这条）
{"type":"PERM_UPDATE","writeEnabled":false,"policy":"whitelist","perm":"rw",
 "sharing":true,"reason":"host_toggled","ts":1698001234}
```

`PERM_UPDATE` 里的 `sharing` 是 M4 补的：主机拨掉共享时，已连接的客户端要能
**立刻**在界面上看到"对方已关闭共享"，而不是等用户点进某个目录才收到 403。

### 5.4 数据通道

独立 TCP（默认 `45456`，被占用则 +1，实际端口随 `DOWNLOAD_ACCEPT` 下发，客户端不预设）。
客户端连上先发 `"QDAT"(4) + token(64B)`——token 是 32 字节随机数的 hex，一次性、5 分钟
过期、绑 transferId；服务端验票后进入裸流，按 256KB 连续下发。**流里不插控制字段**——
取消就 `close()`，读到 EOF 即清理。

实现约定（M5 落地）：

- **背压**：用户态待发数据超过 2MB 就暂停读文件，等 `bytesWritten` 再续。否则一次
  `write()` 几百 MB 全进缓冲，内存飙高且取消要等缓冲排空才真的断开。
- **一条传输一条 TCP**：数据通道无请求分帧，多路复用只会让取消与进度统计变复杂；
  三并发就是三条连接。**M12 之后细化为"一条连接领一段"**：一个文件同时开几条连接由
  设置决定，谁空下来谁去段表里领下一段，段内仍是连续裸流，见 §5.5。
- **令牌一次一用**：取走即从表里删除，重放拿不到第二次。M12 起是**一段一张票**，
  且不能预发（票只有 5 分钟寿命），所以多了 `SEG_REQ`/`SEG_RESP` 这条"来领票"的消息。
- 文件路径、大小、读权限的判定全部在 `DOWNLOAD_REQ` 阶段完成，数据通道只认 token，
  所以端口被同网段扫到也取不走一个字节。

### 5.5 段表与按需领票（M12 第二版）

一个文件同时开 N 条独立数据连接，用来吃满高延迟链路的带宽。**第一版是静态切分**
（段数 = 连接数、每条连接绑死一段），实测有两个毛病：连接速度不均时最后一段单独拖尾；
连接数在传输过程中改不了。第二版改成 **段表 + worker 池**：段数和连接数解耦，
空闲连接去表里领下一段。

**段表只由服务端生成。** 客户端在请求里只表达"我想要几条连接"，其余全部由
`PeerSession` 裁决——两端各算一遍，取整差一个字节就是一份坏文件，而且这种坏只在
最后校验时暴露，排查成本极高。

```
客户端                                     共享端（PeerSession::handleDownloadReq）
DOWNLOAD_REQ{path, offset, fileKey,
             segments:4, segmentDone:[…]}
                                    →   chunkSize = clamp(size/(4×4), 4MB, 32MB)
                                        planChunks(size, chunkSize)   // ≤128 段
                                        ↓
                                    ←   DOWNLOAD_ACCEPT{
                                          token/offset/length,          // 兼容老客户端
                                          chunkSize, segmentCount,
                                          segments:[{index,offset,length,done}, …] }
```

**段长为什么是"总数 / (连接数 × 4)"**：每条连接要连领 4 段才有机会在别人收尾时
还剩活干，否则仍然回到"一条慢连接拖尾"。再用 4MB 下限挡住小文件被切得太碎、
32MB 上限挡住段表过大，`kMaxChunks = 128` 兜底。

**票必须按需领。** `DataGrant` 是一次性的、5 分钟过期、取走即删——这个设计是为了
防重放，但也意味着**不能**像第一版那样一次性把所有段的票都发出去（传得久了后半截票
全过期）。所以加了一条控制消息：

```
SEG_REQ {transferId, index, done}      ← 空闲连接来领票
SEG_RESP{token, offset, length, done, complete}   // 领到
       |{ok:false, code, message}                 // 410 表已失效 / 400 段号越界 / 401 / 403
```

- 首段的票随 `ACCEPT` 直接下发（`token`/`offset`），省掉一次往返。
- `complete:true` 表示这段其实已经齐了（上次收满但没来得及记账），客户端直接跳过。
- **上传的 `done` 以主机盘上分片大小为准**，客户端的 `done` 不算数；
  下载的 `done` 取两边更靠前的那个（客户端在写分片文件，只有它知道真实进度）。

**worker 池**：`TransferTask` 维持 `m_workersTarget` 条连接，任何一条空下来就
`pumpWorkers()` 按序号领下一条 `Pending` 段。一段传完立刻领下一段，所以
"连接数"是并发上限而不是硬绑定——`setWorkerCount()` 加数量立刻补开连接，
减数量只标记、不打断在传的段。

**单段失败不废整份**：某条连接断了只把这段退回队列（`kMaxChunkRetries = 3`），
换条连接重领，服务端按盘上分片大小接着收。第一版"任一段失败整组作废"的写法
会让 worker 池的重试逻辑永远跑不起来。

- **上限与下限**：`kMaxWorkersHint = 8`（对齐界面可调范围）、`kMinChunkBytes = 4MB`。
  文件小于段长时自动退化成单段——多开连接只会多付握手成本。
- **兼容**：顶层 `token`/`offset`/`length` 字段保留，`segments` 为空即意味着单段，
  老客户端不认识 `segments` 也照常下载（只是不分段）。
- **限速共存**：每个 `TransferSegment` 独立领令牌，连接数只提高并发度，
  总速率仍被同一个 `RateLimiter` 令牌桶压住，不会穿透。

## 6. 文件传输与断点续传

### 6.1 三个"必须一致"

1. **身份一致** — `fileKey = SHA-256(size + mtime + 首1MB + 末1MB)`，大文件秒出
2. **偏移一致** — 请求带 `offset`，服务端 `seek(offset)` 起发，不重传
3. **字节一致** — 全量 SHA-256 比对（M13 起摘要与传输同时算，见 §6.6），不一致则判失败并删半成品，绝不静默当成功

### 6.2 下载

```
1. 建 Task(Queued)，查 ResumeStore 得 resumeOffset（.qdpart 实际大小）
2. DOWNLOAD_REQ(offset=resumeOffset, fileKey=上次的 key) → DOWNLOAD_ACCEPT(port, token, size, fileKey)
   - 服务端重算 fileKey，对不上直接 `409`：源文件已被替换，接着写只会拼出坏文件
3. 连数据端口，发 QDAT+token，从 offset 处续写 `<目标>.qdpart`
   （**用 `ReadWrite` 打开**：`WriteOnly` 在部分实现上会顺手截断，前半截变成全零——大小对、内容全错）
   分段时每段写自己的 `<目标>.qdpart.seg<i>`，见 §6.7
4. 每写一块更新已写字节，300ms 节流刷新 QML 进度/速度/ETA；每 4MB 把断点写进 ResumeStore
5. 收满 size → rename 正式名 → **本地摘要此时已在合并/接收中算好** → 与随表下发的摘要比对（见 §6.6）
   - 一致 → Completed；不一致 → 删文件、判 Failed（绝不静默当成功）
6. 失败/暂停/断网（6 秒无数据）→ 保留 qdpart，状态置 Paused，写 ResumeStore
7. 进程被杀 → 下次启动 `restoreResumable()` 按库里的记录把任务恢复成「已暂停」，用户点继续才续
```

**0 字节文件**：段表为空，主机**不发票**（`DOWNLOAD_ACCEPT.token` 为空、`segmentCount=0`），
客户端第 3 步整段跳过——自己建一个空 `.qdpart`、补上常量摘要 `e3b0c442…`，直接进第 5 步比对。
客户端的应答校验写成 `token 为空 && size > 0` 才算"信息不完整"，否则 0 字节文件会在
`主机返回的下载信息不完整` 上直接失败（M13 之前踩到的正是这个）。

### 6.3 上传

对称。服务端写入 `<共享目录>/<uploadDir>/<name>.qdpart`，`UPLOAD_ACCEPT` 返回服务端实际 `currentOffset`（以服务端为准，客户端 offset 仅作参考）。上传落点由 `ShareService::uploadDir()` 决定，见 §7.4。

```
客户端                                              共享端
1. UPLOAD_REQ(name, size, fileKey)          →  2. 三级权限判定 → 选落地名 → 定 offset
   ←  UPLOAD_ACCEPT(port, token, name, path, offset)   （offset 由主机算，客户端照抄）
   （客户端从这一刻起后台算源文件摘要，算好后随 SEG_REQ / CHECKSUM_PUSH 送给主机）
3. 连数据端口，QDAT+token，从 offset 起写裸流
4. 收满 size 或收到主机 UPLOAD_DONE
   ←  UPLOAD_DONE(ok, size, sha256)      ←  5. 收满 → rename 正式名 → 摘要（边收边算）与声明值比对
```

**0 字节文件**：第 3 步没有字节可发（客户端 `startUpload` 直接进"等确认"），所以主机在第 2 步
落地后就自己收尾——`DataServer::finishEmptyUpload` 建空文件、回 `UPLOAD_DONE{ok:true, sha256=e3b0c442…}`，
客户端拿它跟本端源文件摘要比。不走这条特例的话，主机永远等不到那条数据连接，
收件箱里会留一个没人收尾的 `.qdpart.key`，而客户端一直等到 60 秒兜底才收场。

**落地名与续传位点的分配（`PeerSession::handleUploadReq`）**

1. 文件名 `sanitizeUploadName`：去目录、去 `<>:"|?*` 与控制字符、去尾部点与空格、限长 128、
   拒绝以 `.qdpart` 结尾（否则客户端的临时文件会伪装成正式文件）
2. 落点固定 `<shareRoot>/inbox`，用 `SafePath::resolve` 再校验一次（不信任 `dir` 字段）
3. 选名：同名 `.qdpart` **存在且 fileKey 一致**、且该落点没被别的传输占着 → 续传，沿用现有 offset；
   否则 `name (n).ext` 找一个空位
4. fileKey 不一致 → 直接删旧 `.qdpart` 与 `.qdpart.key`，从 0 开始
5. 磁盘剩余 < 2 × 文件大小 → `507`，不建任何临时文件

`.qdpart.key` 是 `.qdpart` 的**侧文件**，只存一行 fileKey。没有它就分不清"上次那个半成品"和
"另一个同名但内容不同的文件"——续上去就是拼一个坏文件出来。

**并发同名上传**：`DataServer::m_reservedPaths`（finalPath → transferId）在授权阶段就占位，
第二个同文件的请求拿不到同一个落点，只能等名字顺延；释放时机是 `unregisterUpload`
（完成/取消/中断）与授权过期 `purgeExpired`。

**收尾（`DataServer::completeUpload`）**

- 校验 `.qdpart` 实际大小 == 声明大小，不等 → 判失败并保留半成品（可续）
- 删同名正式文件（重传覆盖）→ `rename` → 删 `.qdpart.key` → 摘要（从 0 开始时是边收边算的，
  续传才回退到 `ChecksumCache` 读一遍）→ 与客户端声明的摘要比对，不一致删副本
- 结果回 `UPLOAD_DONE`；客户端**只有**收到 `ok:true` 才把任务置 Completed
- 进入"收尾"后就不再接受主机侧中断：`abortByHost` 看到 `m_completing` 直接忽略并记一条日志。
  这时候字节已经全在盘上、文件也已改名，"中断"只会制造一个假暂停；客户端的**显式取消**照旧生效

**客户端侧的几条硬规矩**

- 上传**不写断点库**：断点在主机手里（`.qdpart` 的字节数就是断点），客户端重启后想续传，
  重新发一次 `UPLOAD_REQ` 就能拿回 offset，本地再存一份只会两边不一致
- **校验失败绝不删源文件**：下载失败删的是半成品，上传失败删的就是用户的原始数据
- 上传的"继续"= 本地把旧任务置 cancelled（**只改本地状态**）+ 重新 `uploadPaths()`：
  真正的断点在主机那边，重新申请一次就拿回 offset。**不要在这里发 `CANCEL`**——
  `CANCEL` 会让主机把 `.qdpart` 删掉，续传就变成从头再来
- 60 秒没收到 `UPLOAD_DONE` → 降到 Paused 并在备注里写明"等主机确认超时"
- 写权限被关 / 主机 abort → 统一收敛成 Paused（保留断点），不能显示成 Failed 后还弹一句
  迟到的 `UPLOAD_DONE{ok:false}` 把状态再翻一次

### 6.4 状态机

```
                 ┌──────── 暂停 ────────┐
                 ↓                      │
Queued → Connecting → Transferring → Verifying → Completed
              │             │            │
              ↓             ↓            ↓
           Failed ←──── Interrupted ────┘
                          │
                     Canceled（删临时文件）
```

- **暂停**：关数据连接，保留 qdpart；**中断**：网络异常自动重试 3 次（1/3/6s 退避）后转 Paused
- **取消**：置 Canceled → 关连接 → 发 CANCEL → 删 qdpart 与记录
- 并发：上传/下载各默认 3，可配 1–8；速度用 1 秒滑动窗口，ETA = 剩余/均速

### 6.5 断点库（ResumeStore）

```sql
CREATE TABLE resume (
  peer_id TEXT, remote_path TEXT, peer_name TEXT,
  local_path TEXT, name TEXT, file_key TEXT,
  total INTEGER, done INTEGER, updated_at INTEGER,
  PRIMARY KEY (peer_id, remote_path));
```

- **主键用 (peerId, 远端路径)**，不用内存任务 id：进程重启后 `t-3` 已经指不回任何东西，
  而"哪台主机的哪个文件"是稳定的。
- `done` 只作参考：恢复时以 `.qdpart` 的**实际大小**为续传起点（检查点每 4MB 一次，
  被杀时库里必然落后几 MB；用库里的小值会重收，用文件大小才不浪费）。
- 完成 / 取消 / 校验失败 → 立即销账；启动时 `prune()` 清掉 `.qdpart` 已消失的死记录。
- 恢复出来的任务**一律停在 Paused**：应用一启动就自动往外拉数据，用户会以为自己在被偷带宽。

### 6.6 校验的两侧（M13 修订：摘要计算前置）

| 侧 | 做法 | 为什么 |
|---|---|---|
| 发送端（下载=主机） | 受理 `DOWNLOAD_REQ` 的那一刻就把整文件 SHA-256 排进 `QtConcurrent`，`ChecksumCache` 按 `fileKey` 缓存 | 流量跑起来的同时摘要也在算，收尾时它早就好了；放在 `PeerSession` 线程里算会把整条控制通道一起卡住 |
| 发送端（上传=客户端） | `TransferTask::startSourceHash()` 开工即后台算源文件摘要，随 `SEG_REQ`/`CHECKSUM_PUSH` 送过去 | 与发送并行，最后一个字节发出时摘要已就绪 |
| 接收端 | 本地摘要"顺手"算：多段在**合并分片那一遍**算；单段从 0 开始时**边收边算**（`TransferSegment` 内联 `QCryptographicHash`） | 这两遍读原来就要做，等于白拿一个摘要 |
| 兜底 | 单段 + 续传（前半段不在本次连接里）→ 收完按 4MB/tick 读一遍 | 这种情形没法增量算，但也不能因此放弃校验 |
| 降级 | 推送/补拉都拿不到对端摘要 → 只校验大小，并在任务备注里写清 | 不能让任务永远卡在"校验中" |

**摘要怎么跟着表走**（都不额外占往返）：

```
DOWNLOAD_ACCEPT{..., sha256?}     命中缓存时当场给
SEG_RESP{..., sha256?}            算好了就捎带
CHECKSUM_PUSH{transferId, sha256} 传输途中算好主动推（新增消息号 26，老端忽略）
SEG_REQ{..., sha256?}             上传方向：搭"领段票"的顺风车
```

**不一致的处理**（两条方向都落到"删副本 + 判失败"，但**谁删**不同）：

- 下载：客户端比对本地摘要 vs 主机值 → 不等则删落地文件、任务 Failed，备注"内容与主机不一致，已删除"。
- 上传：**主机**比对（合并时算出的 vs 客户端声明的）→ 不等则删自己收到的副本，回
  `UPLOAD_DONE{ok:false, checksumMismatch:true}`；客户端据此直接判 Failed，**不进可续传暂停**
  （重试同样的内容只会再错一次），并且**绝不删用户源文件**。
- 收尾时摘要若只差几毫秒没到：先等 500ms 宽限（`kChecksumGraceMs`），过了才发 `CHECKSUM_REQ` 补拉；
  总上限 30s，超时降级。

### 6.7 分段落盘与合并（M12）

多段并行后，**"进度 = `.qdpart` 大小"这个前提没了**——各段是乱序落盘的。
取舍两条：不引入位图（位图要自己保证原子性，被硬杀就会和实际字节对不上），
而是让**每一段自己就是一个文件**，分片大小天然就是权威进度。

| 端 | 中间产物 | 完成时 |
|---|---|---|
| 下载 | `<目标>.qdpart.seg<i>` + `<目标>.qdpart.qseg`（元信息：总大小、段数、段长） | 按序合并进 `.qdpart`（**顺手算摘要**）→ 核对大小 → 改名落地 → 删分片与元信息 |
| 上传（主机侧） | `<partPath>.seg<i>` + `<partPath>.qseg` | `UploadGroup` 聚合 → 合并（**顺手算摘要**）→ 校验 → 改名 → 与声明值比对 → **只发一次** `UploadDone` |

- **合并放在 `TransferTask` / `DataServer::finalizeUploadGroup` 里串行做**（1MB 缓冲顺序读、
  追加写），4 段 24MB 的合并耗时在百毫秒级，不值得为它开线程池。
- **合并前逐段核对长度**：分片短了才是常见故障（连接早断、进程被杀），直接进合并
  只会得到一句"大小校验失败"，看不出是哪一段的问题。缺段/短段要在日志里点名。
- **聚合进度节流 500ms**：8 段各报各的，不节流会把 QML 抽屉刷成抖动动画。
- **按段号记账**：`UploadGroup::finished[]` 是 `QVector<bool>`，不是简单的
  `++finishedCount`。同段被重复上报（重连、重试）不会把"到齐"提前，否则会在还有段
  在写的时候就去合并，拼出一个长度不足半截的文件。
- **单段失败不废整组**：`uploadSegmentFailed` 在多段场景下只记一条警告就返回，
  等客户端重领这一段；只有 `keepPart=false`（主机主动取消/中断）才整组收尾。
- **落点占位要还**：`m_reservedPaths` 在最后一条连接走掉时必须释放，否则客户端
  "暂停 → 继续"重新申请同名文件会因为占位还在被判成忙，只能退到 `up (1).bin`
  从头再传一遍，断点等于白留——**这个坑实测踩过**。
- **续传要能认出多段的半成品**：多段落地前根本没有 `.qdpart` 本体（只有 `.seg<i>`
  和 `.qseg`），所以"是不是断点"的判断必须同时认 `.qseg`，只认 `.qdpart` 会让暂停过的
  多段上传永远续不上。
- **续传**：`ResumeStore::prune()` 必须认 `.qdpart` / `.qdpart.qseg` / `.qdpart.seg0`
  三种形态，否则多段断点会被当成死引用清掉；`TransferManager::restoreResumable()`
  是"有 `.qdpart` 就取它的大小，否则累加 `.seg0..63`"。
  **这两个坑都实测踩过**：表现是跨进程续传直接退出码 3、`RESUME_TEST_EMPTY`，
  而进程内暂停/继续一切正常——很容易误判成协议问题。
- **段长变了怎么办**：续传时沿用 `.qseg` 里记的段长（否则盘上分片和段表对不上号）；
  总大小或段数变了、或 `fileKey` 变了，就清掉旧分片从 0 开始，绝不拿不同切法的分片去拼。
- **分片文件从 0 长起**：`DataStreamer::startUpload` 里"本段已有字节"必须用
  `已有 = 本次写位置 − 段基址（segBase）` 换算，不能拿"本段还要收多少"去比——
  段过半时前者必然大于后者，会把收了一半的分片直接删掉重收。

## 7. 配对码、鉴权与上传权限（新增）

### 7.1 信任模型

| 状态 | 能做什么 | 怎么进入 |
|---|---|---|
| **未配对** | 只能看到设备在线、看到"未共享/未配对"，**列不了目录** | 默认 |
| **已配对 · 只读(ro)** | 列目录、看元数据、下载 | 配对码校验通过 |
| **已配对 · 可写(rw)** | 以上 + 上传（**还需主机把顶部"写权限"总开关拨到开**） | 主机在配对时或事后单独勾选"允许上传" |
| **已拉黑** | 什么都做不了，且不再出现在主机列表 | 主机一键撤销 |

关键点：**配对码只解决"信任"，读写权限是独立的一层**。默认配对成功给 `ro`，是否 `rw` 由共享端决定，两者不混为一谈。

### 7.2 首次配对流程（6 位码 + HMAC 挑战应答）

```
共享端 B                                    客户端 A
  │ 生成 6 位码 123456（120s 有效）             │
  │ 弹窗：「我的笔记本 请求配对」                │
  │       「配对码 123456   允许上传 ☐」         │
  │                                            │
  │ ←──────── PAIR_REQ {peerId, name} ──────── │  A 点"未配对"的主机
  │ ───────── PAIR_CHALLENGE {nonce} ────────→ │
  │                                            │  用户输入 6 位码
  │ ←── PAIR_RESP {nonce, mac=HMAC(code,nonce+peerId)} ── │
  │ 校验 mac（并检查码是否过期、尝试次数）        │
  │ 通过 → 生成 token(32B) 写入 TrustStore       │
  │ ───── PAIR_OK {token, tokenId, perm:"rw"} →│  A 存 TrustStore
```

- 配对码由**共享端**生成并显示（凭"能看到对方屏幕"证明物理邻近），不是客户端自己随便填
- 传输的永远是 `HMAC(code, nonce+peerId)`，配对码本身不上网；nonce 一次性
- 失败返回 `PAIR_FAIL {remaining}`，**连错 5 次锁 60 秒**（`429`）
- 配对码可手动"换一个"（重新生成并作废旧码）

### 7.3 后续连接鉴权

```
HELLO → HELLO_ACK{nonce} → AUTH_REQ{tokenId, mac=HMAC(token,nonce)} → AUTH_RESP{ok, perm}
```

- token 同样**不裸传**，走挑战应答
- 共享端 `TrustStore` 存 `(peerId, tokenId, token, perm, lastSeen)`；客户端存 `(peerId, tokenId, token)`
- 撤销配对 = 删记录 + 断开该 peer 所有会话；下次连接返回 `401`，客户端提示"已取消授权，请重新配对"
- 主机改权限或拨动写权限开关 → 主动推 `PERM_UPDATE{writeEnabled, policy, perm}`，客户端界面立即联动，无需重连

### 7.4 写权限：一个随手可拨的总开关 + 两层细化

权限分三层，自上而下短路判定：

| 层级 | 控件 | 位置 | 作用 |
|---|---|---|---|
| **L1 总开关** | `writeEnabled`（默认 关） | **主界面顶部工具条，紧挨共享开关** | 关 = 一切上传 403，无视白名单 |
| **L2 策略** | 仅白名单 / 已配对皆可传 | 设置页 | 决定总开关打开时"谁"能写 |
| **L3 单设备** | 每台设备 `ro / rw` | 已配对设备页 | 白名单策略下逐台授权 |

判定顺序（`PeerSession::handleUploadReq`）：

```
if (!shareEnabled)            → 403 "未共享"
if (!writeEnabled)            → 403 "主机已关闭接收文件"
if (policy == Whitelist && perm != rw) → 403 "未获写权限"
else → 通过
```

**为什么把"关闭上传"从策略里提出来做成开关**：策略是配置（改之前会想一想），开关是状态（随手拨）。用户临时不想收东西时，不该去设置页翻三层菜单。原来的"关闭上传"模式取消，等价于总开关关。

**切换瞬时行为（即时生效，不等重连）**

| 动作 | 服务端 | 客户端 | 界面反馈 |
|---|---|---|---|
| 拨到 **关** | 拒绝新 `UPLOAD_REQ`；**进行中的上传立即中断，保留 `.qdpart`**（等同暂停，可续传）；**已收满、正在算摘要的那条不中断**（没有后续字节可停，文件已落地） | 收 `PERM_UPDATE{write:false}`，上传按钮置灰并提示"对方已关闭接收" | 主机顶部提示"写权限已关闭，N 个上传已暂停" |
| 拨到 **开** | 按 L2/L3 重新判定，接受新请求 | 收 `PERM_UPDATE{write:true}`，按钮恢复 | 提示"已开始接收文件" |

- 选择"立即中断"而不是"让在传的传完"：开关的语义必须干净——用户关掉它就是不想再收字节，含糊的"传完这一个"会让状态难以解释。中断保留断点，重新打开后由用户手动继续，不自动续传（避免违背用户意图）
- 状态同步双通道：未连接的设备靠组播 `ANNOUNCE.write`；已连接的设备靠 `PERM_UPDATE`
- 总开关状态持久化到 `QSettings`，重启后保持；但**首次启动默认关**

**配套规则（与开关无关，始终生效）**

- 上传落点固定 `<shareRoot>/inbox/`（可改），**不允许客户端指定任意目录**
- 文件名去路径、去非法字符、限长 128，重名自动 `name(1).ext`
- 单文件大小上限可配（默认不限），磁盘剩余 < 2×文件大小时直接 507
- 上传中的 `.qdpart` 对下载列表隐藏

### 7.5 安全清单

- **目录穿越**：`SafePath::resolve(root, rel)` 必须 `cleanPath` 后校验 `canonicalPath` 以 `root` 开头；拒绝 `..`、绝对路径、盘符、符号链接逃逸
- **令牌**：数据通道一次性 token，5 分钟过期，绑 transferId
- **限流**：配对 5 次/分钟，鉴权失败 10 次/分钟，超限断开 IP
- **最小权限**：共享默认 `ro`，写权限总开关默认关，两层独立
- **日志脱敏**：不打完整路径与 token 到 logcat / 控制台
- 本期不做 TLS 传输加密（内网 + 配对码已能挡住误连），协议预留 `protoVer` 后续升级

### 7.6 实现备注（M3 落地时确认）

- **删除也是写操作（M14）**：`DELETE_REQ` 直接复用 `canUploadFor(perm)` 这套三级判定
  （共享开 + 写权限开 + 白名单/rw），不另造一套权限语义；再加 `SafePath::resolve` 路径沙箱、
  只删普通文件、共享根不可删。客户端也先挡一次（按钮置灰），但**以服务端判定为准**。
- **双条件放行**：`verified`（码算对）与 `approved`（主人点允许）是两件事，两个都成立才发令牌。
  即使码被旁人看到，也必须主机主人点一下才生效；主机点「允许」时决定给 `ro` 还是 `rw`。
- **摘要计算**：配对 `HMAC(code, nonce + 客户端peerId)`，鉴权 `HMAC(token, nonce)`；
  比对走常量时间，避免逐字符短路。`tokenId` 也参与校验（防止同 peer 多令牌时张冠李戴）。
- **令牌落库**：`trust.db`（SQLite，WAL），两张表——`trusted_clients`（谁可以访问我）与
  `trusted_hosts`（我配对过谁）。token 明文存库（本机文件系统即信任边界），但绝不进日志与网络。
- **端口顺延**：TCP 45455 被占用时 +1 重试（最多 10 个），实际端口回写进 `ANNOUNCE.ctrlPort`，
  客户端才能连对地方。同机多实例联调时天然用到这条。
- **必须禁用系统代理**：局域网 P2P 不能走 `http_proxy`（企业代理 / VPN 客户端常设），
  否则 `QTcpSocket::connectToHost` 会报 *The proxy type is invalid for this operation*。
  已在全局（`QNetworkProxy::setApplicationProxy`）与每个 socket 上双重设置 `NoProxy`。
- **401 自愈**：主机撤销授权后，客户端下次鉴权收到 401，会**自动删除本地令牌**并回到「未配对」，
  等用户重新配对，不会卡在“反复失败”的状态。
- **不主动骚扰**：客户端连上但没令牌时只停在「未配对」，`PAIR_REQ` 必须由用户点「配对」触发，
  避免一选主机就让对方弹窗。
- 实测：错码返回 `remaining` 提示；连错 5 次锁定 60 秒；写权限总开关翻转后
  已连接设备在 1 秒内收到 `PERM_UPDATE` 并把上传能力从 1 变 0。

### 7.7 实现备注（M7 落地时确认）

- **判定顺序落在服务端**（`PeerSession::handleUploadReq`）：未鉴权 `401` → 未共享 `403`
  → `!writeEnabled` `403 "主机已关闭接收文件"` → 白名单策略下非 `rw` `403 "未获写权限（只读设备不能上传）"`
  → 数据通道未起 `500`。文案分开写，客户端能直接显示"对方关了接收"还是"我没被授权"。
- **开关拨到关的动作序列**：`ControlServer::setShareState` 比较前后值 → 由开到关时调
  `DataServer::abortUploads(reason)`（断数据连接、**保留 `.qdpart`**）→ 再广播 `PERM_UPDATE`。
  顺序不能反：先广播后断连，客户端会有一瞬间以为"还有权限但连接莫名其妙没了"。
- **关共享同样中断上传**，理由同开关语义：连目录都不让看了，还接着收字节说不通。
- **客户端收 `PERM_UPDATE` 就地更新**：`peerCanUpload` 变 false 时上传按钮置灰、`uploadHint`
  写明原因；不用重连、不用重新列目录。
- **顶栏"写权限"在没有共享时是禁用态**：两个开关是串联的，共享关着还允许拨写权限只会让人困惑。
- 实测（同机双实例 + CLI 钩子，见 README「联调与自测」）：
  - 768 MB 上传到 65% 时拨关写权限 → 主机日志"已中断 1 个上传：主机已关闭接收文件（断点已保留）"，
    客户端 `paused` 且 `error=主机已关闭接收文件`，收件箱留 525,860,864 字节 `.qdpart` 与 `.qdpart.key`
  - 重新打开后再传 → 主机日志"从 525860864 起"，完成后 SHA-256 `6ca57e82…` 与源文件一致
  - **字节已收满、正在算摘要时**拨关写权限 → 主机日志"上传已收满、正在校验，忽略本次中断"，
    客户端照常 `completed`（这一刻没有后续字节可停，文件已改名落地，按"中断"处理反而会让
    客户端显示暂停、而收件箱里躺着一份完整文件，用户点继续还会再传一份 `name (1)`）
  - 未鉴权 `UPLOAD_REQ` → `401`；ro 身份 → `403`；关着总开关但设备是 rw → 仍 `403`
  - 取消上传（进度 20%）→ 收件箱零残留
  - 并发同名上传 → 落地为 `note.txt` 与 `note (1).txt`，两份 19 字节内容 SHA-256 相同
  - 多文件并发（19 B + 1 MB + 60 MB）→ 三条任务各自 Complete，摘要全部与源文件一致
  - 0 字节文件 → 直接完成，`sha256=e3b0c442…`（空内容摘要）

### 8.4 交互细节

- 双击目录进入，双击文件下载
- **拖拽上传（M8）**：整个窗口是 `DropArea`（`keys: ["text/uri-list"]`），拖入时压一层遮罩 + 中央提示卡片，写着「松手即可上传 / 文件会存到「X」的收件箱」；
  - 不能上传时卡片改成警示色，直接说明原因（未连接 / 对方关闭接收 / 只读设备），**不发请求**，免得用户松手后才被拒
  - 只接文件：目录、非 `file:` URL 一律忽略并提示「只能拖入本机文件（不支持目录）」，不静默吞掉
  - 8 位色在 Qt 里是 `#AARRGGBB`（alpha 在前），写成 `#RRGGBBAA` 会变成全透明——遮罩第一版就是这么失效的
- 本机页头有「收件箱」快捷按钮（`App.openInbox()`）：上传落点不在接收目录树里，不看提示找不到
- 未配对主机在列表里显示锁图标，点击弹"输入配对码"
- 对方写权限关闭时，上传按钮置灰并显示"对方已关闭接收"；本机页头挂一条 `uploadHint` 说明原因
- **关写权限 / 关共享的二次确认（M8）**：开关拨到关且 `incomingCount > 0` 时先弹确认框，写明「当前有 N 个上传正在接收，关闭会立刻中断它们；断点会保留」。
  - 用户点「继续接收」时开关必须**拨回去**：`ToggleChip` 内部 Switch 的 `checked` 绑定会被用户点击打断，光改外层 `checked` 拨不动，所以 `ToggleChip` 提供 `reset()` 直接改内部 Switch
  - 没有进行中的上传时不弹框：拨一下就生效，多一步确认反而碍事
- **关闭窗口（M8，收尾时修订）**：默认**直接退出**——最初默认「关窗收进托盘」，用户点 × 之后
  以为程序退了，进程还在后台收发，这是反直觉的。托盘常驻改为显式打开（设置勾选或 `--tray-on-close`）。
  **有传输在进行时关窗永远先确认**：`busyTransfers = transferActiveCount + incomingCount`，
  校验中的任务也计在内——字节收完了但 SHA-256 还没核对完，这时退出同样该让用户知道。
  「仍要退出 / 收进托盘继续」二选一，确认后放行。窗口 × 与托盘「退出」统一走 `requestQuit()`；
  托盘组件只发信号不自己 quit，否则确认流程被跳过。
  托盘不可用时不能收进托盘——窗口一藏用户就再也找不回来了
- **完成通知（M8）**：窗口在前台 → 窗口内 Toast（3.8 秒自动消失）；在后台或最小化 → 托盘气泡；托盘也没有 → 退回 Toast。Android 走 `SystemNotifier`（JNI 通知栏）
- **界面语言（M8）**：设置里「中文 / English / 跟随系统」，切换后立即生效，不需要重启
  - 中文是源语言，不装 translator；其它语言装 `:/i18n/qdownload_en.qm`
  - `retranslate()` 只重算绑定里的 `qsTr()`；C++ 侧在构造时 `tr()` 成字符串的属性（面包屑根节点）必须在 `setLanguage` 里手动重建
  - **状态标签拆成两份**：`statusBadge` 给人看（跟着语言变），`statusKind`（`upload`/`readonly`/`unshared`/`offline`）给界面判断颜色与分支。QML 里原本写 `badge === qsTr("可上传")`，等于让样式依赖译文——英文下 `PeerInfo` 的译文上下文与 QML 不同，颜色会悄悄变错
  - `PeerInfo` 是值类型（要进 `QVariant` 与容器），不继承 `QObject`，翻译走 `QCoreApplication::translate("PeerInfo", …)`
- **共享目录 / 接收目录自选（M8 收尾）**：设置里各一行 `DirPicker`（更改 / 恢复默认），底层是
  `QtQuick.Dialogs` 的原生 `FolderDialog` + `App.directoryIssue()` 体检
  - 换共享根**立即对已连接会话生效**：`ControlServer` 持有的 `HostContext` 是共享指针，改完别人刷新就是新目录；进行中的上传落点早已定死，不受影响。共享开着时切换补一条 Toast
  - 换接收目录后本机列表回根重列；正在传的任务继续写旧目录，断点也留在旧目录
  - 体检规则：磁盘根目录拒绝；与另一目录**相同或互为父子**拒绝（否则"下载完立刻被共享出去"，列举时互相看见对方的半成品）；**实际试写一次**才放行——Windows 的 `QFileInfo::isWritable()` 只看「只读」属性不看 ACL，`C:\Windows\System32\config` 都返回"可写"，不试写拦不住
  - 命令行 `--receive-root` 与 `--share-root` 同款（本次运行覆盖，不落盘）

### 8.5 托盘与通知

- 托盘图标用 `Qt.labs.platform` 的 `SystemTrayIcon`，**单独放在 `TrayIcon.qml` 并用 `Loader` 加载**：这个模块在没有 StatusNotifier 的 Linux 上会加载失败，写在 `Main.qml` 里会连主界面一起拖垮
- 菜单项：显示主窗口 / 共享（✓ 前缀而非 checkable，原生菜单的勾选态点击后不一定跟随绑定刷新）/ 接收别人上传 / 传输中 N 项 / 退出
- `SystemTrayIcon.available` 由 QML 探测后回填给 `App.trayAvailable`，C++ 不猜平台能力
- `SystemTrayIcon` **不是 Item，没有默认属性**：`TrayIcon.qml` 里不能写任何子元素
  （`menu` 是具名属性所以能写）。想加图标加载探测只能放到 `Main.qml` 里
- **图标资源必须挂在 `qml/` 树下**：`qt_add_qml_module` 把资源铺到 `<前缀>/包名/` 底下，
  QML 里 `../assets/...` 解析到的是 `<前缀>/qml/assets/...`；图标若写在 `assets/icons/tray.svg`，
  实际路径是 `<前缀>/assets/...`，两边错开 → 图标加载失败且**完全静默**（`QQuickIcon` 不报错），
  表现就是"托盘可用但什么都不显示"。已在 `Main.qml` 放一个 0×0 的 `Image` 探针负责告警
- 托盘不可用时的降级路径：关闭窗口 = 正常退出，通知 = 窗口内 Toast，功能不残废
- **收进托盘的提示要走气泡**：窗口已经藏了，窗口内的 Toast 看不见；改 `tray.notify()`，托盘不可用才退回 Toast
- Android 没有托盘概念，`AndroidService` 挂前台服务（常驻通知）保证后台传输不被冻结，见 §9

## 9. 多平台适配

| 议题 | Windows | Linux | Android |
|---|---|---|---|
| 数据目录 | **优先程序目录 `data/`**（`DataPaths`，可写即便携）；不可写退回 `%APPDATA%/qdownload` | 同左；不可写退回 `~/.local/share/qdownload` | apk 目录只读，必然走回退 → app 私有目录 |
| 记录内容 | 信任库 `trust.db`、断点库 `resume.db`、设置 `settings.ini`、日志 `logs/` 全部同根；首次便携启动从系统位置**复制迁移**（不删旧文件） | 同左 | 同左 |
| 共享目录选择 | `FolderDialog` | `FolderDialog` | 私有目录默认；其他位置走 SAF 授权映射 |
| 存储权限 | 无 | 无 | 11+ 需 `READ_MEDIA_*`；只用私有目录可零权限 |
| 防火墙 | 首次监听弹窗；给 `netsh advfirewall` 提示 | `ufw` 提示 | 无 |
| 后台保活 | 托盘常驻 | 可选 systemd user service | **必须前台 Service + 常驻通知**，否则熄屏被杀 |
| 组播 | 正常 | 正常 | 必须 `MulticastLock` |
| 打包 | `tools/package_windows.sh`（`windeployqt`） | `tools/package_linux.sh`（便携包 + deb） | `tools/package_android.sh`（APK/AAB） |
| 特有坑 | 长路径 >260、中文路径 | 无 | Doze、进程回收、文件选择器权限 |

**Android 前台服务（M8 已落地，已真机验证）**：Qt 6 没有公有的 Service 封装，所以在 `android/` 包模板里写了一个 Java `TransferService`（`android/src/org/qtproject/example/qdownload/TransferService.java`），由 C++ 的 `AndroidService::start/stop` 用 JNI 启停。

- 触发条件：`transferActiveCount() > 0 || incomingCount > 0` 就启，全部结束就停——不在后台白占一个通知位
- 清单里必须同时有：`FOREGROUND_SERVICE`、`FOREGROUND_SERVICE_DATA_SYNC`（Android 14 起按类型校验）、`POST_NOTIFICATIONS`、`CHANGE_WIFI_MULTICAST_STATE`
- 包名 `org.qtproject.example.qdownload` 必须与 `Manifest` 的 `service android:name`、Java 文件的 `package` 三者一致，否则服务起不来
- Android 13+ 通知还需用户在系统里授权，未授权时 `SystemNotifier::notify()` 返回 false，界面退回窗口内 Toast
- 打包步骤与脚本用法见 §14

**路径统一**：所有路径经 `PlatformPaths` 转换，业务层内部一律 `/` 分隔，禁止在 C++/QML 里硬编码分隔符。

**校验前置（M13 已实测）**：24MB 多段下载 —— 主机日志「摘要已推送」出现在传输途中，客户端「分片已合并…摘要 xxx」后紧接着「校验通过」，收尾无额外读盘、无 `CHECKSUM_REQ` 往返 / 1MB 单段下载走「边收边算摘要（单段，从 0 开始）」→「摘要已随接收算完」，同样零收尾读 / 12MB 多段上传 —— 主机「收到上传摘要」在合并前到达，合并后「上传校验通过」，客户端 2ms 内收到 `UPLOAD_DONE` / **陈旧摘要**（源文件内容被改、size 与 mtime 与首末 1MB 保持不变 → `fileKey` 不变、缓存摘要过期）→ 客户端「摘要不一致」→「校验失败：内容与主机不一致，已删除」，落地目录为空 / 收尾时摘要只差几毫秒 → 先等 500ms 宽限，推送到达即取消补拉 / **0 字节**：上传由主机 `finishEmptyUpload` 当场落地并回 `UPLOAD_DONE`（收件箱零残留，重传自动 `name (1).bin`）；下载无票无段，客户端自建空文件、摘要 `e3b0c442…` 比对通过

**分段边界**：`planChunks(总长, 段长)` 的区间必须首尾相接无空洞无重叠（口径：`Σlength == total` 且 `offset[i+1] == offset[i] + length[i]`）/ 段数触顶 `kMaxChunks` 时剩余全塞最后一段 / 总长为 0 / 段长 > 总长（单段） / 总长恰为段长整数倍

**异常**：对端离线 / 端口占用 / 磁盘满 / 无写权限 / 组播被拦（手动加 IP）

**性能**：千兆网单文件 > 60 MB/s；QML 列表 2000 项滚动不掉帧

## 13. 已定稿决策

| 决策 | 结论 |
|---|---|
| UI 框架 | **QML / Qt Quick**，Qt 6.12，C++ 内核 + QML 表现，`QML_SINGLETON` 桥接 |
| 文件浏览形态 | 平铺列表 + 面包屑（放弃树形，三端统一） |
| 上传 | **开放**，但需 `perm=rw`，落点 `<shareRoot>/inbox/` |
| **写权限控制** | **顶栏常驻总开关 `writeEnabled`（默认关）+ 策略（白名单/全部已配对）+ 单设备 rw**，三级短路判定；拨动即时生效，进行中的上传立即中断并保留断点 |
| 鉴权 | **6 位配对码** → HMAC 挑战应答 → 长期令牌 + 权限分级 |
| 默认权限 | 配对成功 = `ro`；`rw` 需主机显式授予 |
| 本机页浏览范围 | **接收目录**（`AppLocalDataLocation/downloads`），与共享根刻意分开：一个是自己看的，一个是给别人看的 |
| `fileKey` 计算时机 | **列表不计算**（200 项 × 2MB 随机读会卡死），由 `STAT_REQ` / `DOWNLOAD_REQ` 按需算一次并缓存 |
| 主机关闭共享 | **不断已有连接**，改由 `PERM_UPDATE{sharing:false}` 通知 + `LIST_REQ` 返回 403；这样拨回来对方不用重连 |
| 传输加密 | 本期不做，协议预留版本位 |
| **多网卡组播发送（M8）** | 每张网卡一个专用 `QUdpSocket` 并 bind 到它的 IPv4 地址；**不用** `QNetworkDatagram::setInterfaceIndex`（Windows 上返回成功但包发不出去） |
| **默认界面语言（M8）** | 默认**中文**，不跟随系统：不少中文用户的 Windows 显示语言是 en-US，跟着系统走会一打开就是英文。想跟随系统需在设置里显式选 |
| **托盘不可用时的降级（M8）** | 关闭窗口 = 正常退出（绝不隐藏），通知 = 窗口内 Toast。宁可不做托盘，也不能让窗口"消失" |
| **关写权限/关共享的确认（M8）** | 只在**有进行中上传**时弹；平时拨动立即生效，不多一步 |
| **关窗口默认退出（M8 收尾修订）** | 原先默认"关窗收进托盘"，实测反直觉：点 × 之后用户以为程序退了，进程却还在后台收发。改为**默认退出**，托盘常驻要显式打开；**有传输时仍必问**（含正在校验的任务） |
| **托盘组件不自 quit（M8）** | 托盘「退出」只发信号，交给主窗口的 `requestQuit()`；组件自己 `Qt.quit()` 会跳过主窗口的确认与清理 |
| **QML 连接不开 ignoreUnknownSignals（M8）** | 拼错的信号会被静默吞掉。这次正是靠它发现 `SystemTrayIcon.availableChanged` 在 QML 侧连不上（Qt 6 未导出 NOTIFY），改由派生属性通知 |
| **托盘图标挂在 qml/ 树下（M8）** | `qt_add_qml_module` 会把资源平移到 `<前缀>/包名/` 底下，写 `assets/icons/tray.svg` 时实际路径与 QML 的相对 URL 错开，图标静默加载失败。改为 `qml/assets/icons/tray.svg`，并加 0×0 Image 探针在失败时告警 |
| **目录可写要试写才知道（M8 收尾）** | Windows 的 `QFileInfo::isWritable()` 只反映「只读」属性、不查 ACL，系统保护目录也返回 true。换共享根/接收目录前用 `QTemporaryFile` 在目标目录实际落一个文件，失败即拒绝；试探失败时把刚 mkpath 出来的空目录清掉 |
| **共享根与接收目录互斥（M8 收尾）** | 两目录**相同或互为父子**一律拒绝：混在一起会"下载完立刻被共享出去"，列举时互相看见对方正在写的半成品。例外：当前设置已陷入嵌套时不再拦，否则用户两边都改不了、彻底卡死 |
| **记录数据跟程序走（M8 收尾）** | `DataPaths::init()` 在打开任何文件前判定：程序目录下 `data/` **真实试写**成功 → 便携模式（trust.db / resume.db / settings.ini / logs 同根，拷走即带走全部状态）；写不进去（Program Files、Android）→ 退回系统目录，设置走原生位置。首次便携启动把旧位置的数据**复制**过来（不删，兼顾同机新旧版本共存）。判定用试写而不是 `isWritable()`——后者在 Windows 上不看 ACL |
| **Android 原生接口的正确 include（M8 收尾）** | 不存在 `<QNativeInterface>` 头文件，`QNativeInterface::QAndroidApplication` 声明在 **`QtCore/qcoreapplication_platform.h`**。它是**头文件缺失**而非链接问题，加 `Qt6::Gui` 无效（`Qt6::Quick` 本就依赖 Gui）。`context()` 返回 `QtJniTypes::Context`（`JObject<Tag>`，不继承 `QJniObject` 但有 `operator QJniObject()`），故调用点写法不用改 |
| **`Q_OS_ANDROID` 分支必须单独编 Android（M8 收尾）** | 桌面编译会把整段 Android 代码预处理器跳过，写错也零告警（本次 `QJniObject(QStringLiteral(...))` 就是这样藏到打包才炸的）。约定：改 `Q_OS_ANDROID` 分支后必须跑一遍 `cmake --build <android 构建目录> --target qdownload`，`.so` 编过才算完 |
| **Android 出包的环境门槛（M8 收尾）** | ① **manifest 里不许写 `<uses-sdk>`**：AGP 9 起 manifest merger 直接失败，版本只能由 CMake 的 `QT_ANDROID_MIN_SDK_VERSION`(28) / `QT_ANDROID_TARGET_SDK_VERSION`(36) 下发；② minSdk 必须 ≥ 28（Qt 6.12 deploy 校验），target 不要写没装过的平台（会联网下载）；③ Qt 6.12 模板固定 Gradle 9.5.1 + AGP 9.2.1，**要求 JDK 17+**（本机 JDK 11 会报 `Gradle requires JVM 17 or later`），故出包固定 `JAVA_HOME` 指向 JDK 21。Android 上控件回退 Basic 风格，与桌面 Windows 风格外观不同。已实测出包：`android-build-qdownload-release-unsigned.apk`（84MB，release 未签名） |
| **Q_INVOKABLE 不能当"会刷新的状态"用（写权限摘要）** | 状态栏的「写权限：关/白名单/全部已配对」原来是 `Q_INVOKABLE writeSummary()`——QML 对它只求值一次且不建立依赖，开关怎么拨都停在旧值（只有颜色在变，因为颜色绑的是带 NOTIFY 的 `writeEnabled`）。改成 `Q_PROPERTY(writeSummary READ ... NOTIFY writeSummaryChanged)`，在写权限/策略/语言三处变化时发通知；QML 侧三处调用从 `App.writeSummary()` 改成属性访问 `App.writeSummary`。**原则：要在界面上跟着变的值必须是属性** |
| **传输并发数可调 + 排队（M8 收尾）** | 设置新增 `transfer/threads`（1–16，默认 3，SpinBox 只认 `valueModified`——挂 `valueChanged` 会在初始化钳制时把设置写坏：创建时 value 先被钳到 from 再触发一次 changed，把 3 写成 1）。实现：`activeTransferCount()` = 活跃任务 + 在途申请（只数任务会被连点穿透）；下载并发满时**不发 DOWNLOAD_REQ** 先排队（授权包里是一次性 token+端口，拿久了会失效），任务 finished/changed（暂停/取消）时 drain；上传从"满了直接拒绝"改成同样排队。`--get` 改为可重复，配合 `--pair-test` 一次发多个下载验证排队时序 |
| **本端名称可改（M8 收尾）** | 设置面板置顶一节，保存后同时换三处身份（`ControlServer::setHostIdentity` / `ControlClient::setSelf` / `DiscoveryService::setSelf`）并 `announceNow()`，对方不用等心跳。空串=恢复默认主机名（`net/deviceName` 键删除）；上限 32 字；`--name` CLI 是硬覆盖，设置了它界面改名无效（`--set-name` 会拒绝并提示） |
| **单文件连接数可调（M12）** | 设置 `transfer/segments`（1–8，默认 3）+ `--segments` 临时覆盖 + `--workers-at pct:count` 验证动态调整。**做成了段表 + worker 池**，而不是"段数 = 连接数、每条连接绑死一段"：静态切分下连接速度不均时最后一段单独拖尾，连接数也没法在传输中改。段表与区间只由服务端裁决，客户端只报"我想要几条连接"——两端各算一遍取整差一字节就是坏文件。票必须**按需领**（`SEG_REQ`/`SEG_RESP`）：票 5 分钟过期、取走即删，预发会让后半截票全过期。落盘用"每段一个分片文件 + 一份 `.qseg` 元信息"，**不引入位图**——位图要自己保证原子性，被硬杀就和实际字节对不上；分片大小本身就是权威进度。顶层 `token/offset` 字段保留，`segments` 为空 = 单段，老客户端不受影响 |
| **手动断开挂起自动重连（M8 收尾）** | 「断开」= `disconnectPeer()`：**先**置 `m_manualDisconnect` 再断链，否则 disconnected 推回 Idle 后 3 秒内心跳就把它拉回去了。挂起只被三件事解除：点「重连」（`connectToSelectedPeer`）、换选主机（`setSelectedPeerId` 且 id 变化）、进程重启。**掉线重连不受影响**——主机消失再出现仍自动连，两条路径都有 `PAIR_TEST_CONN` 状态流水实测 |
| **Android 分区存储适配（M8 收尾后补）** | 安卓 10+ 能用 File API 读写的只剩内部 files 与**应用专属外部目录**；系统目录选择器返回 `content://` 授权 URI（QFile 打不开）且不过滤无权限的公共目录，这就是「改目录提示没有权限」的来源。对策：①出厂默认目录落 `AndroidStorage::preferredDir()`（应用专属外部目录）；②安卓弃用系统对话框，改用**内置目录浏览器**（`DirBrowser.qml`），只列「试写通过」的根（应用专属/内部存储），支持逐级浏览+新建文件夹；③想要任意位置走「所有文件访问权限」（`MANAGE_EXTERNAL_STORAGE`，跳系统设置页由用户开，`hasFullAccess()` 用 `Environment.isExternalStorageManager()` 轮询；Android 9/10 走 `WRITE_EXTERNAL_STORAGE` 运行时权限）；④**启动自愈** `repairUnusableRoots()`：上次存的目录这回写不了就退回出厂默认并提示，避免界面"拨了开关没反应"。候选根在列出前逐一试写，注定被拒的位置根本不摆出来。排障口子：`--demo-dir-browser` 在桌面强制走这套浏览器，把整条交互链先在真机前过一遍。**QML 坑：Popup 自带 `enter` 过渡属性，自定义函数撞名会被静默吞掉**（只剩一条 warning），改名才生效 |

## 14. 打包与分发（M11 脚本化）

三个平台各一个入口脚本，共用 `tools/common.sh`（Qt 前缀探测、JDK 主版本判定、
统一的日志格式）。都支持 `--check`（只自检环境、不构建）与 `--skip-build`（只重新打包）。

| 平台 | 命令 | 产物 |
|---|---|---|
| Windows | `bash tools/package_windows.sh` | `dist/qdownload-<版本>-win64/` |
| Linux | `bash tools/package_linux.sh` | `dist/qdownload-<版本>-linux-<架构>.tar.gz` + `dist/qdownload_<版本>_<架构>.deb` |
| Android | `bash tools/package_android.sh [-a <abi>] [--aab] [--install]` | `dist/qdownload-<版本>-android-<abi>.apk` |

### 14.1 Linux 的四个取舍

| 决策 | 原因 |
|---|---|
| **只搬 `libQt6*` / `libicu*`** | libc、libX11、libGL 与发行版强绑定，一起搬反而更容易起不来（linuxdeployqt 挨骂最多的点）。系统库留给目标机 |
| **不用 patchelf** | 改用 `AppRun` 里的 `LD_LIBRARY_PATH` + `usr/bin/qt.conf` 的 `Prefix = ..` 相对路径。少一个外部工具依赖，只有 CMake + Qt 的机器也能跑完打包 |
| **用 `qmlimportscanner` 挑 QML 模块** | 只搬 import 到的模块（`QtQuick`、`QtQuick.Controls`…），扫不到就整棵 `qml/` 一起搬并给警告 |
| **先装到 `dist/.staging-*` 再换上** | 打包中途失败时，dist 里上一个能用的包还是完整的 |

`assets/icons/qdownload.svg` 与 `packaging/linux/qdownload.desktop` 由 CMake 的
`install()` 规则装进 `usr/share/...`（仅在 `UNIX AND NOT ANDROID` 时生效，
不影响 Windows / Android 构建）。

### 14.2 Android 的三道门槛

打包脚本会自动定位并逐项报「可用 / 缺失」，缺什么就明确说怎么补：

1. **JDK 17+**：Qt 6.12 模板固定 Gradle 9.5.1 + AGP 9.2.1，Gradle 9 不支持 JDK 11。
2. **SDK / NDK**：`ANDROID_SDK_ROOT` 若没设就扫常见位置，并**优先选带 NDK 的那份**
   （机器上常同时装着 Qt Creator 自带的、只有 platform-tools 的那一套）。
3. **签名**：没 keystore 就只能出**未签名**包，真机装不上（
   `INSTALL_PARSE_FAILED_NO_CERTIFICATES`）。先跑 `tools/android_keystore.sh`
   生成 keystore 与 `signing.env`，`source` 之后再打包即可出签名包。
   四个 `QT_ANDROID_KEYSTORE_*` 变量缺一个就报错，不静默退化。

另有两条硬约束（CMake 侧已处理）：manifest 里**不许写** `<uses-sdk>`
（AGP 9 起 manifest merger 直接失败），minSdk 必须 **≥ 28**（Qt 6.12 deploy 会校验）。
